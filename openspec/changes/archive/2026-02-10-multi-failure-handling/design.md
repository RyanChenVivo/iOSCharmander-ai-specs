## Context

`analyzing-uitest-failures` skill 目前針對單一失敗進行分析，輸出單一建議。當 CI 有多個失敗時，用戶需要重複執行分析流程，無法快速掌握全貌。

現有流程：
1. 讀取失敗資料
2. Pattern matching + History check
3. 輸出單一建議（Observe/Investigate/Fix/Restore）
4. 用戶選擇動作

目標流程：
1. 讀取**所有**失敗資料
2. 對每個失敗執行 Pattern matching + History check
3. 彙整結果並分組
4. 輸出摘要視圖
5. 用戶選擇要處理的群組

## Goals / Non-Goals

**Goals:**
- 提供多重失敗的整體摘要視圖
- 按建議動作分組，方便批次處理
- 識別可能同源的失敗，避免重複分析
- 低風險動作（Observe）支援批次處理

**Non-Goals:**
- 不改變現有單一失敗分析邏輯
- 不新增自動修復功能
- 不支援跨 CI build 的失敗聚合

## Decisions

### Decision 1: 分組層級

**選擇：** 兩層分組 — 先按建議動作，再按同源判斷

**替代方案：**
- 單層分組（只按動作）：太粗糙，無法識別同源問題
- 三層分組（動作 → 模組 → 同源）：過於複雜

**理由：** 兩層分組平衡了資訊密度和操作便利性。

### Decision 2: 同源判斷優先級

**選擇：** Pattern ID > 測試名稱前綴 > 錯誤訊息關鍵字

**理由：**
- 相同 Pattern ID 是最強的同源信號
- 測試名稱前綴反映功能模組歸屬
- 錯誤訊息關鍵字可能是巧合，僅作輔助參考

### Decision 3: 批次處理策略

**選擇：** 依動作風險決定

| 動作 | 策略 | 理由 |
|------|------|------|
| Observe | 批次 | 低成本，只是記錄 |
| Restore | 批次 | 通常是同一環境問題 |
| Investigate | 逐一 | 需要截圖確認各自原因 |
| Fix | 逐一 | 每個可能需要不同修復 |

**替代方案：**
- 全部批次：高風險動作可能導致錯誤處理
- 全部逐一：低風險動作效率太低

### Decision 4: 摘要輸出格式

**選擇：** 分組詳細式，每個測試顯示錯誤摘要

**理由：** 用戶希望看到整體資訊但不需要展開就能了解每個測試的狀況。

## Risks / Trade-offs

**[Risk] 同源判斷誤判** → 僅作為建議，用戶可選擇逐一處理

**[Risk] 摘要過長** → 當失敗數量超過 10 個時，考慮折疊顯示

**[Trade-off] 批次 Observe 可能遺漏細節** → 可接受，因為 Observe 本身就是等待觀察的低成本動作
